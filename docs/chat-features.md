# 聊天功能与应用消息

## 日常使用

- 草稿按话题加密保存在当前中心或设备的 SQLite；停止输入约 400 ms 后保存。保存正文、回复目标和单调更新版本，迟到的保存请求不会恢复已经发送的草稿。重新解锁后可恢复，不自动同步到其他设备。
- 聊天界面默认加载最近 50 条；「加载更早的消息」保留滚动位置。搜索结果与回复引用可以加载目标附近的历史。常规刷新读取增量变更，不再重复拉取全部会话。
- 未读分割线记录本次进入会话时的第一条未读；超出当前分页时可以跳转。阅读旧消息时显示底部新消息按钮，点击后加载最新一页。
- 消息作者可以编辑普通文本或撤回。编辑替换正文并显示「已编辑」；撤回清除消息正文、保留占位，不允许后续编辑恢复正文。原消息 ID、发送者、时间和回复关系保持稳定。
- 话题置顶、标签和「待讨论 / 进行中 / 已解决」状态由双方共享并同步到关联设备。置顶优先排序，标签支持筛选。归档话题需要先恢复才能修改。

## 普通文件邀请

文件邀请是普通 `Event::Message`，不是特殊消息。`format` 为 `file`，`body` 是下面对象的 JSON 字符串；UI 将它渲染为文件卡片：

```json
{
  "version": 1,
  "fileId": "<UUID>",
  "name": "报告.txt",
  "mime": "text/plain",
  "size": 12345,
  "sha256": "<64 位 SHA-256 hex>",
  "chunkSize": 24576
}
```

邀请消息没有文件内容。发送前，文件按 24 KiB 分块、用本机密钥加密暂存；单文件上限为 16 MiB。接收方需要主动点击接收。文件名不允许路径和控制字符，下载使用固定的二进制 MIME 与 attachment 响应，不自动执行、打开或覆盖接收方文件。

## 统一特殊消息

控制操作由独立的加密 `Event::Control` 承载，线上的 `type` 为 `control`。事件包含 `operation_id`、`topic_id`、`topic_title`、`created_at` 和 `body`；`body` 是下面统一对象的 UTF-8 JSON 字符串：

```json
{
  "version": 1,
  "kind": "message.edit",
  "data": {
    "messageId": "<目标消息 UUID>",
    "body": "新的正文",
    "revision": 1791180000000
  }
}
```

完整事件示例：

```json
{
  "type": "control",
  "operation_id": "<操作 UUID>",
  "topic_id": "<话题 UUID>",
  "topic_title": "工作",
  "created_at": 1791180000,
  "body": "{\"version\":1,\"kind\":\"message.withdraw\",\"data\":{\"messageId\":\"<消息 UUID>\",\"revision\":1791180000000}}"
}
```

普通 `Event::Message` 的正文永远不作为控制载荷解析。粘贴控制 JSON、旧的 `cipherwhisper.special\n` 前缀或编辑后的正文均保持为文本，不会修改历史、话题或授权文件；指定普通消息的显示 `format` 也不能提升为控制事件。控制分发由经过签名、加密路由绑定的事件类型决定，继续校验发送者、话题、目标作者与文件授权。UI 只通过独立的 `/special` API 发起操作；设备使用独立的 `Operation::Control`，普通 `Send` 在中心和设备缓存中始终作为普通消息处理。

`version` 是应用载荷版本，不改变 Olm / Envelope 版本。正常识别的控制载荷不作为独立聊天记录保存；在 ratchet 与接收确认的同一事务中直接修改对应消息、话题或文件状态。保留操作的版本和 ID，用于处理重复或迟到更新，不保留控制消息原文。未知版本、未知类型、格式错误以及权限不合法的操作保留为「未知消息」，UI 用转义的纯文本展示原始 body，不执行它。

| kind | data | 行为 |
| --- | --- | --- |
| `message.edit` | `messageId`, `body`, `revision` | 仅原作者可以修改同一话题内的普通文本 |
| `message.withdraw` | `messageId`, `revision` | 清空原作者消息正文，保留撤回占位 |
| `topic.meta` | `pinned`, `tags`, `status`, `revision` | 修改共享话题属性 |
| `file.accept` | `fileId`, `offerId` | 接收方授权对应文件传输 |
| `file.chunk` | `fileId`, `offerId`, `acceptId`, `part`, `hex` | 传输已授权文件的一个分块 |

本机在发送编辑、撤回与话题属性操作时生成单调毫秒版本。相同版本通过操作 ID 确定顺序；撤回不可被迟到的编辑恢复。目标消息尚未收到时不确认该操作，也不提交 ratchet，发送方可以重试；错误载荷不会阻止其他消息继续接收。

## 文件真正传输的过程

1. 发送普通文件邀请，双方历史各保留一个文件条目。
2. 接收方发出 `file.accept`；接收确认直接更新文件条目的授权状态，不新增聊天记录。
3. 发送方检查邀请 ID、文件 ID、话题和接收者身份。重复确认共用由邀请与接收者身份派生的 consent ID，不会创建多个传输。
4. 后台每轮最多将两块内容放入现有加密 outbox，未投递队列达到约八项时暂停生产。`file.chunk` 继续通过 Olm 加密、签名确认与既有重试机制传输，没有另开明文文件通道。
5. 接收方仅处理来自邀请发送者、绑定已授权 consent ID 的分块，按编号持久化，允许相同内容重复、乱序与重启后续传。分块更新文件卡片，不作为聊天消息保存。
6. 收齐后检查块数、长度和整个文件的 SHA-256。通过校验才开放下载；失败显示错误。零字节文件也需要授权并校验。

关联设备通过中心的认证 TLS 同步文件状态及分块，下载时再次校验文件哈希；设备端发送的文件由暂存该文件的设备生产分块，所以该设备和中心都需要运行才能继续发送。

历史正文和已接收的文件分块延续现有本地明文历史的存储模型；待发送源文件及草稿加密保存。撤回修改聊天历史与搜索索引，不保证删除已复制、下载、备份或旧设备同步快照中的内容。

## 兼容范围

支持 `Event::Control` 的客户端遇到未来载荷版本或操作类型时显示未知消息与原始数据。尚未支持此事件的旧程序会拒绝它，普通 `file` 消息或新增设备同步实体也可能被拒绝。使用这些功能前应更新通信双方和关联设备。

旧前缀实现已排队的 Markdown 控制载荷在新版本中按普通文本处理；需要用户重新发起对应操作。已有历史不会因正文内容被重新执行。
